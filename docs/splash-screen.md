## Provider-scope startup correction

The user observed a Riverpod assertion after the splash transitioned to MaterialApp.router. Launch overrides adConfigurationProvider and firebaseStartupStatusProvider in a nested ProviderScope; the ad providers and router had no declared scope dependencies, so Riverpod attempted to reuse their parent-container instances.

The scoped inputs now opt in with dependencies: []; adConsentProvider declares its gateway, adAnalyticsProvider declares configuration/Firebase/consent inputs (including deferred canLog reads), adMobServiceProvider declares its configuration/consent/gateway/Analytics chain, and routerProvider declares startup/ad service dependencies. This ensures the navigation observer and AdRuntime resolve the same child-scoped service. No ad eligibility, consent, production flags, telemetry rules or IDs were changed.

Regression tests in test/ads/ad_provider_scope_test.dart pre-initialize parent providers, apply nested launch overrides, and check service/configuration/Analytics/router identity, parent isolation and zero ad requests. A second case checks Firebase-only scoping of the deferred Analytics gate. These tests use fake ad/consent gateways without live Firebase.

Actual checks are in verification/provider-scope/: pub get, formatting, analysis and tests were attempted but blocked by SDK cache permissions; AdMob source checks pass. Runtime confirmation remains outstanding. Fully stop and restart the app to exercise fresh provider containers after this change.
